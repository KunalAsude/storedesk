# Deploy — staging and production (free tier)

```
Browser ─► Vercel (web)  ──/api/*──►  Render (API, Docker)  ──►  Neon (Postgres)
develop ─► Vercel Preview   ─► storedesk-api-staging (sleeps when idle) ─► Neon branch "staging"
main    ─► Vercel Production ─► storedesk-api (kept awake by a pinger)   ─► Neon branch "main"
```

- **Why `/api/*` goes through Vercel:** the browser only ever talks to the web's domain, so the refresh cookie is first-party (Safari blocks cookies between `vercel.app` and `onrender.com`). With a custom domain later, nothing changes: point the domain at Vercel.
- **Deploys are automatic:** merge into `develop` → staging; release PR `develop` → `main` → production. Render waits for CI to pass. The protected `main` branch is the production approval.
- **Migrations** run when the API container starts (`apps/api/Dockerfile`). A failed migration stops the new container and the old version keeps serving. Migrations must be backward-compatible: add first, remove in a later release.
- **Secrets** live only in the Render / Vercel dashboards (and your password manager). Never in the repo, chat or tickets.

## One-time setup (≈ 20 min)

### 1. Neon (database)
1. [console.neon.tech](https://console.neon.tech) → **New project** `storedesk`, Postgres **16**, region **AWS Asia Pacific (Singapore)**.
2. **Branches → New branch** `staging` from `main`.
3. For each branch, **Connect** → copy the **pooled** connection string (host contains `-pooler`). You need 2 strings: `main` (production) and `staging`.

### 2. Render (API)
1. [dashboard.render.com](https://dashboard.render.com) → **New → Blueprint** → pick the `storedesk` GitHub repo, branch **`main`** (so `render.yaml` changes reach production only with a release; staging still deploys from `develop`). Render reads `render.yaml` and creates `storedesk-api` and `storedesk-api-staging`. `render.yaml` must be on `main` first, so do this after the first release PR.
2. When asked for the `sync: false` values:
   - `storedesk-api` → `DATABASE_URL` = Neon **main** string; `WEB_ORIGIN` = your Vercel production URL (from step 3; you can fill it later).
   - `storedesk-api-staging` → `DATABASE_URL` = Neon **staging** string; `WEB_ORIGIN` = the Vercel URL of the `develop` branch.
   - `JWT_SECRET` is generated by Render, a different one per service.
3. Wait for both deploys. Check `https://<service>.onrender.com/health` → `{"ok":true,...}`. If the name was taken, Render adds a suffix: use the real URL everywhere below.

### 3. Vercel (web)
1. [vercel.com/new](https://vercel.com/new) → import `storedesk` → **Root Directory** `apps/web` (framework Next.js is detected; Bun is used from `bun.lock`).
2. **Settings → Git → Production Branch** = `main`.
3. **Settings → Environment Variables**:

   | Name | Production | Preview |
   | --- | --- | --- |
   | `API_URL` | `https://storedesk-api.onrender.com` | `https://storedesk-api-staging.onrender.com` |
   | `NEXT_PUBLIC_APP_STAGE` | `production` | `staging` |

4. Redeploy. **Changing `API_URL` later also needs a redeploy** (rewrites are fixed at build time; a build without it fails on purpose). The staging web is the preview URL of `develop` (`storedesk-git-develop-<you>.vercel.app`). Preview URLs need a Vercel login by default (Deployment Protection); fine for staging.
5. Put both Vercel URLs into the Render `WEB_ORIGIN` values (step 2) if you skipped them.

### 4. Keep production awake during shop hours (free)
Render's **750 free hours/month are shared by all free services in the workspace**. Going over suspends *all* of them, production included, until the month ends. Production awake 24/7 uses ~744 h and would starve staging, so:

[cron-job.org](https://cron-job.org) → new job: `GET https://storedesk-api.onrender.com/health` every **10 min**, **only 07:00–23:00 Asia/Kolkata**. That's ~500 h/month for production (it sleeps at night; the 07:00 ping wakes it before the shop opens) and leaves ~250 h for staging, which sleeps when idle. Check usage under Render → Workspace → Billing once a month.

### 5. Seed production once
Keep the production database URL and passwords out of the repo **and out of your shell history** (don't type them into the terminal):
```bash
touch "$HOME/storedesk-prod.env" && chmod 600 "$HOME/storedesk-prod.env"
code "$HOME/storedesk-prod.env"     # paste the lines below in the editor, save
```
```
DATABASE_URL=<Neon main pooled string>
SEED_SUPERADMIN_NAME=Kunal
SEED_SUPERADMIN_EMAIL=<your email>
SEED_SUPERADMIN_PASSWORD=<strong password>
SEED_OWNER_NAME=<owner name>
SEED_OWNER_EMAIL=<owner email>
SEED_OWNER_PASSWORD=<strong password>
```
```bash
bun --env-file="$HOME/storedesk-prod.env" packages/db/src/seed.ts
rm "$HOME/storedesk-prod.env"       # keep the passwords in your password manager instead
```
Do the same for staging with the staging string and test users.

## Check after each deploy
0. **Staging sleeps:** wake it first by opening `https://storedesk-api-staging.onrender.com/health` directly and waiting for the reply (~1 min). Through the web, the first request may time out (Vercel gives up before Render wakes).
1. `https://<web>/api/health` → `{"ok":true,...}` (proves the Vercel → Render rewrite).
2. **Staging only:** the `yourIp` in that response must equal your real IP ([ifconfig.me](https://ifconfig.me)). If it shows another address, change `TRUST_PROXY_HOPS` on Render (try `1` or `3`) — otherwise all users share one login rate-limit bucket.
3. Render logs show `Migrations applied` then `API on http://localhost:<port>`.

## Known trade-offs (pilot)
- **IP spoofing on direct API calls:** the API is also reachable at `*.onrender.com`. With `TRUST_PROXY_HOPS=2`, a caller there can fake `X-Forwarded-For` and dodge the per-IP login rate limit. The per-account lockout (5 tries → 15 min, unknown emails included) still holds. Fix before taking payments: the web adds a secret header and the API refuses `/auth/*` without it.
- **Migrations use the pooled URL.** Fine for our migrations; if one ever fails through the pooler, run it with Neon's direct (non-`-pooler`) string.
- **One API instance.** Migrations at start and the in-memory rate limiter assume one instance; add a migration lock and a shared limiter before scaling out.

## Roll back
- **API:** Render → service → **Events** → pick the last good deploy → **Rollback**.
- **Web:** Vercel → **Deployments** → last good one → **Promote to Production**.
- **Database:** migrations are not rolled back. That's why they only add; a bad release is fixed forward. Neon can restore a branch to an earlier point in time for real accidents (the free plan keeps only a short window: check it in the Neon console).

## Build and run the API image locally
```bash
docker build -f apps/api/Dockerfile -t storedesk-api .
docker run --rm -p 4100:4000 -e PORT=4000 -e APP_STAGE=development \
  -e JWT_SECRET=local-only-secret-at-least-32-characters \
  -e DATABASE_URL=postgres://storedesk:storedesk@host.docker.internal:5432/storedesk storedesk-api
```
